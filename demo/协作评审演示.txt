多人协作文档演示：校园科研项目评审与发布计划

文档说明
这是一份用于演示多人协作、选区评论、Agent 任务和修改建议审批的纯文本材料。录制演示时，可以让不同账号分别承担项目负责人、研究成员和评审 Agent 的角色。正文中的“待扩展段落”适合选中后发起评论，也可以在同一文档中修改其他段落来观察同步结果。

一、项目背景

我们正在设计一个面向高校科研团队的知识整理与协作写作流程。团队成员需要把访谈记录、实验结果和阶段性结论整理成一份可供导师评审的项目报告。传统做法通常依赖邮件往返和多个文档副本，修改意见分散在不同位置，最终很难确认某个结论是谁提出、哪一版已经处理，以及哪些建议仍然需要负责人决定。

本项目希望把正文、讨论、Agent 建议和审批过程放在同一个协作空间中。人类成员负责判断事实和取舍，Agent 负责发现表达问题、补充论证线索和提出局部修改建议。任何自动修改都必须先以建议的形式出现，经过有权限的成员审核后才会写入正文。

二、项目目标

1. 建立一份结构清晰、可以持续维护的研究报告。
2. 让项目成员能够在同一份文本上并发编辑，并及时看到彼此的修改。
3. 让评论能够定位到具体选区，而不是只停留在整篇文档的笼统讨论。
4. 让 Agent 根据选区、上下文和评论线程提出可审阅的修改建议。
5. 记录建议的提出、接受、拒绝和过期状态，确保每次正文变化都可理解。
6. 在本地文件与协作空间之间保持清晰的同步关系，避免编辑结果只停留在浏览器中。

三、研究问题

本阶段主要回答三个问题：

问题一：多人共同编辑时，怎样保持内容的一致性？

问题二：Agent 怎样在不越权改写全文的情况下，帮助成员扩展一段过于简略的说明？

问题三：当原文已经被其他成员修改时，系统怎样识别旧建议已经失效，并提醒负责人重新判断？

四、当前方案概述

4.1 文档空间

项目负责人创建一个文档空间，并将本地文件夹映射到空间中的文档列表。文件夹中的 TXT 和 Markdown 文件可以被扫描、打开和编辑。协作编辑产生的内容经过保存后写回对应文件，文档名称和相对路径用于帮助成员理解文件的来源。

4.2 成员与权限

文档空间中的成员拥有不同角色。viewer 可以查看内容和讨论；commenter 可以发表评论；suggester 可以提交修改建议；editor 可以直接编辑正文并审批建议；owner 负责邀请成员、管理 Agent 和调整项目设置。Agent 作为一种特殊成员参与讨论，但它的有效权限不能超过触发它运行的人类成员权限。

4.3 评论与任务

普通评论用于讨论问题。任务线程用于明确要求某个 Agent 完成一项工作，例如扩展背景、比较两个方案或检查术语一致性。任务被创建后会关联到指定 Agent，Agent 的回复、建议和运行状态都集中在线程中，方便成员继续追问。

五、待扩展正文

5.1 研究动机

目前的研究动机还不够完整。团队已经观察到多人协作文档中存在意见分散、修改难以追踪的问题，但还没有说明这些问题如何影响实际的科研工作，也没有交代为什么单纯增加一个评论框不能解决它们。

这里需要补充一段文字，说明在真实项目中，信息分散会怎样增加沟通成本、造成版本误判，并进一步解释为什么“正文、评论、Agent 建议和审批”应该放在同一条工作流中。补充内容应该具体、克制，避免把系统描述成能够自动替代研究人员的工具。

5.2 用户流程

一名项目负责人首先创建空间并选择本地项目目录，系统扫描其中的文本文档。负责人邀请研究成员加入空间，为不同成员授予相应权限。研究成员打开报告，在“研究动机”段落中发现说明不足，于是选中需要改进的句子并创建评论。

如果评论中提及 Polisher，Agent 应该读取选区、附近段落、文档大纲和当前线程消息。它可以回复自己的理解，并提出一条或多条局部替换建议。建议不会立即改变正文，负责人需要先查看原文、新文本和修改理由，再决定接受、拒绝或继续讨论。

5.3 质量标准

报告的每个关键结论都应该能够追溯到材料来源或明确的讨论过程。表述应当避免没有依据的绝对化判断，段落之间要有自然的逻辑连接，术语在全文中保持一致。Agent 可以指出表述风险，但不能替成员虚构实验数据、受访者观点或外部来源。

六、协作演示任务清单

任务 A：邀请与加入

由项目负责人邀请一个新的真实账号加入当前空间，并授予 commenter 角色。被邀请成员登录后接受邀请，在不刷新页面的情况下确认成员列表和在线状态发生变化。

任务 B：并发编辑

让负责人在“研究动机”标题下方补充一句项目范围说明，同时让研究成员修改“质量标准”中的一个词。两个浏览器窗口都应看到对方的更新，最终文本保持一致。

任务 C：选区评论

选中下面这句话：
“目前的研究动机还不够完整。”

创建一个范围评论，消息内容可以是：
@Polisher 请把这句话扩展成一段更具体的说明，解释信息分散如何影响科研团队的协作，并保持语气客观。

任务 D：Agent 扩展建议

Polisher 需要先回复它理解的修改目标，再针对允许的选区生成修改建议。建议应当只覆盖“目前的研究动机还不够完整。”这一句或其明确允许的范围，不得顺手改动后面的质量标准。建议理由应该说明新增内容如何连接问题与产品目标。

任务 E：人工审批

由 editor 或 owner 检查 Agent 回复。先观察建议处于 pending 状态，再点击接受，确认正文发生替换；随后在另一个窗口查看同步结果。如果建议不符合项目语气，则选择拒绝，并保留原文。

任务 F：过期建议

在建议产生后，先由另一名成员手动修改被引用的原句，再回到建议面板尝试接受。系统应把无法准确对应当前文本的建议标记为 stale，并提示成员重新生成或重新讨论，而不是悄悄覆盖新内容。

任务 G：本地同步

完成一次人工编辑和一次 Agent 建议审批后，执行同步操作，检查对应本地 TXT 文件是否包含最新正文。重新扫描目录时，文件内容和空间中的文档应该保持一致；如果本地文件在协作期间被外部程序修改，应能看到需要重新判断的状态。

七、评审记录模板

评审人：
评审时间：
使用的文档版本：

1. 事实与范围
- 是否清楚说明了项目要解决的问题？
- 是否避免了无法验证的承诺？
- 是否区分了已完成能力和后续设想？

2. 结构与表达
- 标题层级是否帮助读者定位内容？
- 段落之间是否存在跳跃？
- 术语“空间”“文档”“线程”“建议”“Agent”是否前后一致？

3. 协作体验
- 评论是否准确附着在选区上？
- Agent 是否收到了完整且必要的上下文？
- 建议是否经过人工审批后才改变正文？
- 多个浏览器窗口中的内容是否最终收敛？

4. 本地文件
- 文档是否正确映射到相对路径？
- 写回后文件编码和换行是否保持可读？
- 重新扫描后是否能识别最新内容？

八、下一步计划

第一阶段：完成本次演示流程，记录从创建空间到本地写回的完整操作路径。
第二阶段：根据评审记录，补充缺少的说明，统一术语，并删除重复段落。
第三阶段：邀请更多成员试用，比较不同角色在评论、建议和审批上的体验。
第四阶段：整理真实使用中出现的问题，区分产品流程问题、Agent 输出问题和本地同步问题，再决定下一轮实现范围。

九、演示结束时的结论

这份文档的目标不是展示 Agent 能够一次性写完一篇报告，而是展示一种可检查、可讨论、可审批的协作方式。成员始终能够看到修改对象、修改理由和修改状态；Agent 的作用是缩短发现问题和准备候选文本的时间，最终决定权仍然属于有权限的人类成员。
