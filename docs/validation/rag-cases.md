# RAG 论文协作验收

日期：2026-10-23。三个用例均通过真实选区评论、Codex CLI 生成建议、人工接受与正文核对；本轮未修改产品代码。

## 测试条件

- 输入为用户提供的[原始论文](../examples/rag-paper.md)，仅还原粘贴时转义的 Markdown 标记与换行。文中研究数据未经核实，只作为测试材料。
- 在独立的本地演示数据库中测试，不修改日常项目的数据。Agent 为 Polisher，使用本机已登录的 Codex CLI 与产品默认调用参数；不是 Mock，也没有把预期答案作为模型输入。
- 保留默认 `window` 上下文策略、12,000 字符预算。实际指令只把占位名称 `@agent` 换为 `@Polisher`。
- 三次建议全部生成后才依次接受，所以三次运行看到的正文均为同一份原文。
- 运行记录、原始选区、指令、模型回复、建议文本与重建上下文保存在 [rag-cases.json](rag-cases.json)；接受后的完整文档见 [rag-paper-reviewed.md](../examples/rag-paper-reviewed.md)。

## 结果

| 用例 | 检查结果 | 本次耗时 | 重试 |
| --- | --- | --- | --- |
| 1. 口语化转学术表达 | 通过：去除“大家普遍都在用”“我们搞出来”等表达，保留 `18.4%`，生成待审批建议并成功写回 | 24.073 秒 | 0 |
| 2. 参数段落转表格 | 通过：生成引导语与 8 列、3 行数据的 Markdown 表格；接受后预览显示真实表格，保留 120 / 310 / 890 毫秒和各方案参数 | 26.581 秒 | 0 |
| 3. 结合前文修正结论 | 通过：引用 A / B / C 的三组延迟，给出条件化选择，并指出缺少准确率差值，不能武断决定最优配置 | 27.232 秒 | 0 |

耗时来自这三次 `AgentRun.durationMs`，含本机 CLI 调用与模型处理，不是性能基准或未来响应时间承诺。

### 数据与修改范围

接受三个建议后，通过服务端读取完整正文，与“原文依次替换这三个选区”的结果逐字比较，结果完全一致：没有额外改动，也没有把待审旧文和新文一并写入。

用例 2 中，B / C 的重叠参数在原文未给出，模型写为“未说明”；没有补造数值。浏览器 DOM 显示 8 个列标题、3 行数据，与截图一致；刷新页面后再次读取表格，数据仍完整保留。

用例 3 没有照抄预期答案中的“方案 B 更具性价比”，而是将 B 作为折中候选，并提醒缺少各方案准确率的具体差值。验收依据是数据准确、结论有条件和语义满足指令，不要求逐字匹配预期文案。

### 上下文核对

使用运行时同一个 `buildContext` 实现，以原文、真实选区和实际触发消息重建上下文。三次长度分别为 3130 / 3321 / 3039 字符，均与运行记录的 `inputChars` 一致；三次都包含完整的延迟数据。

当前 `window` 实现除选区、邻近段落和大纲外，还提供全文一致性检查素材。因此用例 3 即使相邻窗口未覆盖完整的第 2.2 节，也能从全文素材读取 120 / 310 / 890。该证据是按实际输入重建并核对记录，不是网络请求抓包；不据此声称超长文档被截断后也一定可见。

## 复现

1. 启动 Riff，将原文导入或粘贴到名称以 `.md` 结尾的文档。
2. 在「成员与 Agent」中将 Polisher 连接到可用的真实模型，保留 `window` 策略。
3. 按 JSON 记录中的 `quote` 逐条选中原文，发表评论，内容使用对应的 `instruction`。
4. 对照数据和语义检查建议，逐条接受；用例 2 切到「预览」确认表格。
5. 对照接受后的正文确认只有相应选区被替换。真实模型再次运行时措辞与耗时可能不同。
